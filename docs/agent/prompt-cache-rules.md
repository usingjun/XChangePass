# Prompt Cache Rules

## 목적

이 문서는 Codex가 XChangePass 프로젝트에서 작업할 때 반복 문맥을 안정적으로 재사용하기 위한 규칙이다.

목표는 매 작업마다 긴 설명을 다시 읽히는 구조를 줄이고, 변하지 않는 문맥과 자주 바뀌는 문맥을 분리하는 것이다.

프롬프트 캐싱은 질문을 저장하는 기능이 아니다.
반복해서 사용되는 긴 문맥 Prefix를 안정적으로 유지해 재사용하는 방식이다.

## 핵심 원칙

Codex에게 매번 전달되는 문맥은 크게 두 가지로 나눈다.

1. 자주 바뀌지 않는 고정 문맥
2. 매 작업마다 바뀌는 최신 문맥

고정 문맥은 가능한 앞쪽에 두고, 최신 문맥은 뒤쪽에 둔다.

## 캐시에 적합한 문맥

아래 내용은 자주 바뀌지 않으므로 반복 문맥으로 유지하기 좋다.

* 프로젝트 개요
* 기술 스택
* 도메인 핵심 규칙
* 송금 정합성 규칙
* 멱등성 Idempotency 규칙
* 장애 거래 복구 Recovery 규칙
* 이상거래 탐지 Fail-Closed 규칙
* 거래내역 통합조회 규칙
* 작업 방식
* 검증 기준
* 보고 형식

따라서 아래 문서는 가능한 자주 수정하지 않는다.

* docs/agent/project-context.md
* docs/agent/xchangepass-rules.md
* docs/agent/task-template.md
* docs/agent/prompt-cache-rules.md

## 캐시에 적합하지 않은 문맥

아래 내용은 자주 바뀌므로 고정 문맥에 섞지 않는다.

* 방금 수정된 코드 diff
* 최신 에러 로그
* 방금 실행한 테스트 결과
* 현재 작업 요청
* 임시 분석 내용
* 특정 버그의 재현 로그
* 이번 작업에서만 필요한 파일 목록
* 아직 확정되지 않은 설계 후보
* secrets 또는 env 파일 내용
* 최신 애플리케이션 로그

이런 내용은 작업 요청의 뒤쪽에 별도로 붙인다.

## 문맥 배치 규칙

Codex에게 작업을 요청할 때는 아래 순서를 따른다.

1. 고정 문서 읽기
2. 현재 작업 대상 설명
3. 관련 파일 또는 코드 위치
4. 최신 에러 로그 또는 테스트 결과
5. 원하는 결과
6. 검증 기준

예시:

```text
AGENTS.md와 docs/agent 하위 문서를 먼저 읽어.

이번 작업은 XChangePass의 멱등성 처리 개선이야.

관련 파일은 TransferService, IdempotencyService, TransferController 쪽을 먼저 확인해.

최근 테스트에서 동일 Idempotency-Key 요청이 동시에 들어올 때 중복 처리 상태 응답이 불안정했어.

코드는 최소 변경으로 수정하고,
동일 키 중복 요청 테스트와 동일 키 다른 본문 요청 테스트를 보강해.

작업 후 ./gradlew test를 실행해.
```

## 문서 변경 규칙

고정 문서는 자주 흔들지 않는다.

문서가 자주 바뀌면 반복 Prefix가 깨지고, Codex가 매번 새로운 문맥으로 인식할 수 있다.

단, prompt-cache-rules.md를 도입한 초기 안정화 중에는 문서가 자주 바뀔 수 있다.
이 기간에는 문서를 v0.x 상태로 관리하고, 규칙이 안정된 뒤 v1.0으로 고정한다.

따라서 문서 수정은 아래 경우에만 한다.

* 프로젝트의 실제 기술 스택이 바뀐 경우
* 도메인 규칙이 바뀐 경우
* 검증 기준이 바뀐 경우
* 반복적으로 같은 실수가 발생해 규칙으로 고정해야 하는 경우
* 기존 문서가 실제 코드와 맞지 않는 경우

단순 작업 메모, 임시 로그, 이번 작업만 필요한 정보는 고정 문서에 넣지 않는다.

## 버전 관리 규칙

문서 버전은 너무 자주 바꾸지 않는다.

주요 도메인 규칙이 바뀌는 경우에만 문서 안에 버전을 명시하거나 올린다.

예시:

```md
# XChangePass Rules

문서 버전: v1.1
마지막 주요 변경: 멱등성 요청 본문 hash 검증 기준 추가
```

버전 변경이 필요한 주요 도메인 규칙 변경은 다음과 같다.

* 송금 트랜잭션 경계 변경
* 멱등성 처리 방식 변경
* 거래 상태 전이 방식 변경
* 복구 배치 기준 변경
* 이상거래 탐지 Fail-Closed 정책 변경
* 통합조회 인덱스 또는 페이징 전략 변경

작은 문장 수정, 오타 수정, 예시 보완, 임시 안정화 조정은 버전 변경 대상이 아니다.

## 캐시 효율을 위한 금지 사항

* 매 작업마다 project-context.md 전체를 다시 고치지 않는다.
* 최신 로그를 xchangepass-rules.md에 붙이지 않는다.
* secrets, env 파일 내용, logs 디렉터리의 최신 로그를 고정 문서에 넣지 않는다.
* 임시 설계 후보를 고정 문서에 넣지 않는다.
* 작업 요청마다 문서 구조를 바꾸지 않는다.
* 확정되지 않은 기술을 기술 스택에 추가하지 않는다.
* 현재 코드에 없는 구조를 문서에 먼저 확정하지 않는다.

## Codex 작업 요청 템플릿

Codex에게 작업을 요청할 때는 아래 형식을 우선 사용한다.

```text
AGENTS.md와 docs/agent 하위 문서를 먼저 읽어.

이번 작업은 [작업명]이야.

관련 도메인은 [송금 / 멱등성 / 복구 / 이상거래 / 통합조회]야.

수정 금지 범위는 [secrets / env / 배포 설정 / 무관한 리팩토링]이야.

관련 파일 후보는 [파일 또는 패키지 후보]야.

최신 문맥은 아래와 같아.
[에러 로그 / 테스트 결과 / 재현 조건 / 최근 변경 요약]

먼저 기존 코드 흐름을 분석하고,
문서의 규칙과 실제 코드가 충돌하는 부분이 있는지 확인해.

그 다음 최소 변경으로 구현해.

비즈니스 로직이 바뀌면 테스트를 추가하거나 수정해.

실행할 검증 명령은 [./gradlew test 또는 관련 테스트 명령]이야.

작업 후 아래를 보고해.

1. 변경 파일
2. 변경 내용
3. 변경 이유
4. 검증 결과
5. 남은 위험
```

## 핵심 요약

* 반복되는 규칙 문서는 앞에 둔다.
* 매번 바뀌는 로그와 요청은 뒤에 둔다.
* 고정 문서는 자주 흔들지 않는다.
* 주요 도메인 규칙이 바뀔 때만 버전을 올린다.
* 임시 정보는 고정 문서에 넣지 않는다.
