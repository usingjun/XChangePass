# XChangePass Rules

## 핵심 원칙

XChangePass의 기준 데이터는 거래 원장 Ledger이다.

지갑 잔액 스냅샷 Wallet Balance Snapshot은 빠른 조회를 위한 데이터다.
하지만 최종 정합성 판단 기준은 거래 원장이다.

따라서 잔액 스냅샷과 거래 원장이 불일치할 수 있는 작업에서는 항상 정합성 검증 기준을 함께 고려한다.

## 송금 정합성 규칙

송금 Transfer 작업에서는 아래 규칙을 지킨다.

* 송신 지갑 잔액 차감, 수신 지갑 잔액 증가, 거래 원장 저장은 하나의 자금 트랜잭션 안에서 처리한다.
* 성공한 송금은 정확히 하나의 거래 원장을 생성해야 한다.
* 실패한 송금은 송신 지갑 또는 수신 지갑에 부분 반영되면 안 된다.
* 송신 지갑과 수신 지갑을 동시에 잠가야 하는 경우 항상 동일한 순서로 잠근다.
* 지갑 ID 기준 오름차순으로 락을 획득해 데드락 위험을 줄인다.
* PostgreSQL Advisory Lock을 사용하는 경우 transaction-scoped lock을 우선 사용한다.
* 락 획득, 잔액 변경, 원장 저장의 트랜잭션 경계를 명확히 유지한다.

## 멱등성 Idempotency 규칙

멱등성이 필요한 송금 요청에서는 아래 규칙을 지킨다.

* 동일 사용자와 동일 Idempotency-Key는 중복 송금을 생성하면 안 된다.
* 동일 Idempotency-Key로 요청 본문이 달라지는 경우 충돌로 판단해야 한다.
* 요청 본문 비교가 필요한 경우 request body hash를 저장해 검증한다.
* 최초 요청 접수 상태는 중복 요청과 구분 가능해야 한다.
* 이미 처리 중인 중복 요청은 송금을 다시 실행하지 않고 기존 처리 상태를 반환한다.
* 이미 완료된 중복 요청은 기존 완료 결과를 반환한다.
* 멱등성 적용 후에는 잔액 변경, 원장 저장, 이상거래 검사 호출이 중복 발생하지 않아야 한다.

## 거래 상태 전이 규칙

거래 상태는 단순 성공/실패만으로 관리하지 않는다.

거래 처리 흐름을 추적할 수 있도록 상태를 단계별로 구분한다.

예시 상태는 다음과 같다.

* REQUESTED
* VALIDATING
* PROCESSING
* COMPLETED
* FAILED

상태 전이 규칙은 다음과 같다.

* 자금 처리 전 단계와 자금 처리 진입 후 단계를 구분한다.
* 실패 시 오류 코드뿐 아니라 실패 단계와 재시도 가능 여부를 함께 남긴다.
* 상태 전이 충돌이 가능한 경우 낙관적 락 또는 조건부 업데이트를 고려한다.
* 완료된 거래는 임의로 실패 상태로 되돌리지 않는다.

## 장애 거래 복구 Recovery 규칙

장애 거래 복구에서는 자동 재처리보다 안전한 분리가 우선이다.

* 자금 처리 전임이 명확한 거래만 자동 실패 처리할 수 있다.
* 거래 상태가 REQUESTED 또는 VALIDATING이고 원장이 없다면 자동 실패 처리 대상이 될 수 있다.
* PROCESSING 상태이거나 원장 존재 여부가 모호한 거래는 자동 재처리하지 않는다.
* 자금 처리 여부가 모호한 거래는 운영 예외 Operational Exception으로 분리한다.
* 복구 배치는 같은 거래를 중복 처리해도 결과가 깨지지 않아야 한다.
* 동시에 여러 복구 작업이 실행되어도 상태가 잘못 전이되면 안 된다.
* 최근 정상 처리 중인 거래를 오래된 미완료 거래로 오판하면 안 된다.

## 이상거래 탐지 Fraud Detection 규칙

이상거래 탐지 실패 시에는 Fail-Closed를 기본 원칙으로 한다.

* Redis 또는 이상거래 탐지 인프라가 불안정하면 송금을 차단한다.
* 이상거래 탐지 실패 상태에서 잔액 변경이나 원장 저장이 발생하면 안 된다.
* Circuit Breaker가 열린 상태에서는 Redis 호출을 반복하지 않는다.
* 장애가 회복되면 HALF_OPEN 검증 후 정상 상태로 복구한다.
* Retry만으로 장애 상황을 버티려고 하지 않는다.
* 장애 상황에서 사용자 자금 상태가 불명확해지는 것보다 거래 차단이 우선이다.

## 거래내역 통합조회 규칙

대용량 거래내역 조회에서는 전체 스캔을 피한다.

* 사용자 기준 조건을 먼저 태울 수 있는 인덱스를 고려한다.
* 거래 시각과 식별자를 함께 사용해 안정적인 정렬 기준을 만든다.
* 대용량 조회에서는 Offset Pagination보다 Keyset Pagination을 우선 고려한다.
* 여러 거래 테이블을 통합 조회할 경우 각 테이블에서 필요한 후보만 먼저 조회한 뒤 병합한다.
* 성능 개선은 평균 응답 시간, p95, 처리량 등 수치로 검증한다.
* 인덱스는 추가만 하지 말고 실제 실행 계획과 결과를 기준으로 유지 여부를 판단한다.

## 테스트 규칙

정합성 관련 변경은 단순 성공 테스트만으로 완료하지 않는다.

### 송금 테스트

* 정상 송금 성공
* 잔액 부족 실패
* 원장 저장 실패 시 롤백
* 동시 송금 시 잔액 오차 0
* 성공 송금 수와 원장 수 일치
* 데드락 미발생

### 멱등성 테스트

* 동일 Idempotency-Key 중복 요청
* 동일 키 + 동일 본문 요청
* 동일 키 + 다른 본문 요청
* 처리 중 중복 요청
* 완료 후 중복 요청
* 중복 원장 미생성
* 중복 잔액 변경 미발생

### 복구 테스트

* 자금 처리 전 미완료 거래 자동 실패 처리
* PROCESSING 상태 거래 운영 예외 분리
* 원장이 존재하는 모호한 거래 운영 예외 분리
* 최근 정상 거래 오종료 방지
* 복구 배치 중복 실행 안전성

### 이상거래 테스트

* 정상 요청 허용
* 지연 발생 시 처리 확인
* Redis 연결 차단 시 송금 차단
* Circuit Breaker OPEN 상태에서 Redis 호출 방지
* 복구 후 HALF_OPEN에서 CLOSED 전환
* 장애 중 잔액/원장 변경 없음

### 통합조회 테스트

* 대용량 데이터 기준 조회 성능 비교
* Keyset Pagination 결과 순서 안정성
* 중복 또는 누락 없는 페이지 이동
* 인덱스 또는 스키마 변경 전후 실행 계획 비교
