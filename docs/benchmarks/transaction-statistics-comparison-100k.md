# Transaction Statistics Benchmark Result - 100k

## 1. Purpose

This document records the 100,000-row Java benchmark result for the XChangePass transaction statistics query modes.

The benchmark compares:

* `GROUP_BY`: direct `UNION ALL + GROUP BY` over the source transaction tables
* `MATERIALIZED_VIEW`: query from `mv_transaction_monthly_statistics`
* `SUMMARY`: query from `transaction_monthly_summary`

It also compares refresh cost for:

* Materialized View refresh
* Materialized View concurrent refresh
* Summary Table refresh

This is a Java runner benchmark. It excludes HTTP, authentication, JSON serialization, and network overhead. The goal is to establish a repository/database-level baseline before k6 API load tests and transfer API mixed-load tests.

This result does not decide Primary/Replica adoption. Primary/Replica should be judged after validating whether statistics queries affect transfer API latency under mixed load.

## 6. Interpretation

For the 100k Java runner benchmark, `MATERIALIZED_VIEW` showed the strongest query performance overall.

For heavy-user 12-month reads:

* `GROUP_BY` average latency: 16.041ms
* `MATERIALIZED_VIEW` average latency: 1.033ms
* `SUMMARY` average latency: 4.721ms

`SUMMARY` was also faster than direct `GROUP_BY` for the heavy-user scenarios, but it was slower than `MATERIALIZED_VIEW` in this 100k run.

For `REGULAR_USERS_12M`, the gap between modes was much smaller. In that scenario, `SUMMARY` was slower than both `GROUP_BY` and `MATERIALIZED_VIEW`. This can be affected by dataset shape, indexes, returned row count, runner environment, and measurement count. Follow-up validation with `EXPLAIN (ANALYZE, BUFFERS)` and PostgreSQL statistics is needed before drawing a broader conclusion.

Refresh cost showed:

* `MV_REFRESH` had the lowest average refresh cost.
* `MV_REFRESH_CONCURRENTLY` was more expensive than regular MV refresh.
* `SUMMARY_REFRESH` had the highest average refresh cost in this run.

`SUMMARY_REFRESH` currently uses a delete/insert refresh style, so follow-up checks should include dead tuple growth, autovacuum behavior, and `pg_stat_user_tables` observations.

This benchmark is repository/database-level evidence only. It is not an HTTP/k6 result and should not be generalized as full API performance or as proof that transfer APIs are unaffected.

## 7. Primary/Replica Decision

Primary/Replica separation is not decided from this result alone.

This benchmark only compares pure statistics query and refresh cost. Primary/Replica adoption requires mixed-load validation with transfer APIs and statistics APIs running together.

Potential Replica candidates:

* Statistics reads
* Summary reads
* Historical transaction reads that tolerate lag

Primary-only targets:

* Balance reads requiring latest state
* Transfer processing
* Ledger writes
* Recovery decisions
* Reconciliation decisions
* Idempotency decisions
* Latest transaction/status decisions

## 9. Portfolio-Safe Summary

The following wording is safe to use because it describes a development and verification benchmark, not production operation:

* PostgreSQL-based transaction statistics reads were implemented and compared across direct `GROUP BY`, Materialized View, and Summary Table approaches using the same dataset.
* In a 100,000-row benchmark, Materialized View showed lower average latency than direct `GROUP_BY` for the heavy-user 12-month statistics query, while Summary Table showed both query improvement potential and refresh cost trade-offs.
* Statistics data was kept separate from latest balance, ledger, recovery, and reconciliation decisions and treated as derived read data with `dataAsOf` semantics.
* Primary/Replica separation was intentionally deferred until statistics API and transfer API mixed-load validation can show whether read traffic affects write-path latency.

Avoid the following claims:

* Improved production traffic
* Improved real user traffic
* Completed Primary/Replica adoption
* Summary Table is always optimal
* Materialized View is always optimal
* Transfer API impact is already proven to be zero
