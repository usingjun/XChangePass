# Transaction Statistics Benchmark Result - 1M Smoke

## 1. Purpose

This document records the 1,000,000-row smoke benchmark result for XChangePass transaction statistics queries.

The benchmark checks the trend of:

* `GROUP_BY`, `MATERIALIZED_VIEW`, and `SUMMARY` query performance at 1,000,000 rows
* Materialized View refresh cost
* Materialized View concurrent refresh cost
* Summary Table refresh cost
* Difference from the previous 100,000-row benchmark

This is a Java runner benchmark. It excludes HTTP, authentication, JSON serialization, and network overhead. It is a repository/database-level baseline before k6 API load tests and transfer API mixed-load tests.

This is not a full 1M benchmark result. The 50-iteration run was attempted but stopped because it did not finish in a reasonable time. The successful result below is a 1M smoke run with 10 measurement iterations.

Primary/Replica adoption is not decided from this result. That decision should wait for k6 mixed-load results that measure whether statistics queries affect transfer API latency.

## 6. Comparison With 100k Result

### HEAVY_USER_12M

`GROUP_BY`:

* 100k average latency: 16.041ms
* 1M smoke average latency: 97.284ms
* Increase: about 6.1x

`MATERIALIZED_VIEW`:

* 100k average latency: 1.033ms
* 1M smoke average latency: 0.860ms
* The read path remained mostly stable.

`SUMMARY`:

* 100k average latency: 4.721ms
* 1M smoke average latency: 2.170ms
* The 1M smoke run measured lower latency, but it used only 10 measurement iterations. p95 and p99 stability should be rechecked with more controlled observation.

## 7. Interpretation

In the 1M Java runner smoke benchmark, long-range heavy-user reads showed that direct `GROUP_BY` is strongly affected by data growth.

`MATERIALIZED_VIEW` reads stayed stable at 1M rows. `SUMMARY` reads were also faster than direct `GROUP_BY` for heavy-user reads, but Summary refresh cost was the largest among the measured refresh paths.

For `REGULAR_USERS_12M`, the query latency gap between modes was small. This scenario returned fewer rows and did not stress the aggregation path as much as the heavy-user scenarios.

`SUMMARY_REFRESH` averaged about 11.8 seconds and reached about 18.9 seconds at p95 in this smoke run. Since the Summary refresh currently uses a delete/insert style, follow-up checks should include dead tuple growth, autovacuum behavior, and buffer usage.

This result is a Java runner smoke result. It is not an HTTP/k6 result. It does not measure transfer API p95 or p99 impact.

Primary/Replica judgment remains deferred. The next step should inspect SQL plans and PostgreSQL statistics with `EXPLAIN (ANALYZE, BUFFERS)` or `pg_stat_statements`, then validate API-level effects with k6 mixed-load tests.

## 8. Primary/Replica Decision

This result alone does not justify Primary/Replica separation.

The current result measures pure statistics query and refresh cost. Primary/Replica adoption requires mixed-load validation with transfer APIs and statistics APIs running together.

Potential Replica candidates:

* Statistics reads
* Summary reads
* Historical transaction reads that tolerate lag

Primary-only targets:

* Balance reads requiring latest state
* Transfer processing
* Ledger writes
* Recovery decisions
* Reconciliation decisions
* Idempotency decisions
* Latest transaction/status decisions

## 9. Follow-up Actions

1. Add `EXPLAIN (ANALYZE, BUFFERS)` for query and refresh SQL paths.
2. Prepare a benchmark-only `pg_stat_statements` environment.
3. Add k6 statistics API read-only load tests.
4. Add k6 transfer API + statistics API mixed-load tests.
5. Decide Primary/Replica necessity based on mixed-load results.

## 10. Portfolio-Safe Summary

The following wording is safe to use because it describes development and verification results, not production operation:

* PostgreSQL-based transaction statistics reads were implemented and compared across direct `GROUP BY`, Materialized View, and Summary Table approaches, and a 1,000,000-row smoke benchmark was used to check query and refresh cost trends.
* In the 1,000,000-row Java runner smoke benchmark, heavy-user 12-month direct `GROUP_BY` reads showed increased average latency as data grew, while Materialized View reads remained stable.
* Summary Table reads showed query improvement potential, but the delete/insert refresh style showed higher refresh cost and requires follow-up observation for dead tuples and autovacuum behavior.
* Statistics data was kept separate from latest balance, ledger, recovery, and reconciliation decisions and treated as derived read data with `dataAsOf` semantics.
* Primary/Replica separation was intentionally deferred until statistics API and transfer API mixed-load validation can show whether read traffic affects write-path latency.

Avoid the following claims:

* Improved production traffic
* Improved real user traffic
* Completed Primary/Replica adoption
* Summary Table is always optimal
* Materialized View is always optimal
* Transfer API impact is already proven to be zero
* Full 1M benchmark completed
